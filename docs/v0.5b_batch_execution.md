# V0.5-B safe batch execution

V0.5-B adds the production execution layer around the contracts and dry-run
planner frozen in V0.5-A. It does not generate conformers, change ligand
chemistry, redefine Vina or interface-scoring semantics, aggregate candidates,
or merge workstation results.

## Execution model

The runner requires one explicit mode: `--dry-run`, `--execute`, or `--resume`.
It performs one Vina process at a time in execution and resume modes. Candidate and conformer order
comes from the canonical V0.5-A plan. A global contract failure stops before an
output root is created. Candidate-scoped preflight, docking, or analysis
failures are recorded independently and do not stop later candidates.

Each successful candidate follows this existing-tool pipeline:

1. validate the V0.5-A candidate plan and formal ligand inventory;
2. create a unique candidate attempt and write its input identity;
3. prepare and audit each standardized input with the V0.4 preparation tools;
4. run and audit each conformer serially with the V0.4 Vina wrapper;
5. generate V0.4 pose metrics;
6. run the frozen V0.4 ensemble analysis;
7. validate the candidate package and publish a completion marker.

Production code contains a real subprocess path, but validation of V0.5-B uses
only injected fakes or mocked subprocesses. No real docking is part of the
V0.5-B release gate.

## Candidate states

The stable states are `PENDING`, `PREFLIGHT_PASS`, `RUNNING`, `COMPLETE`,
`FAILED_PREFLIGHT`, `FAILED_DOCKING`, and `FAILED_ANALYSIS`. State records are
append-only JSON files with an ordinal prefix. A `COMPLETE` state and completion
marker are written only after every required artifact has passed integrity
validation. The completion marker is written and read back first; only then is
the terminal `COMPLETE` state appended. Weak scores, a low eligible fraction, or sparse contacts are valid
scientific outcomes and do not cause a technical failure state.

## Immutable attempts

The on-disk layout is:

```text
<output-root>/
  batch_manifest.json
  batch_runs/<batch-run-id>.json
  candidates/<candidate>/attempts/<attempt-id>/
    attempt_manifest.json
    states/*.json
    workspace/...
    ensemble/<candidate>/...
    completion.json
```

Files are created exclusively. Existing attempt directories are never reused,
deleted, or overwritten, and there is no force option. Attempt IDs combine a
UTC creation timestamp with a digest of the complete candidate execution
identity, so they are unique and auditable.

## Resume contract

`--resume` is conservative. A candidate is skipped only when a completed
attempt validates all of the following:

- candidate ID, group, sequence, template, receptor, and comparison protocol;
- canonical manifest, screening protocol, receptor registry, and ligand
  inventory IDs and raw-byte hashes;
- required conformer inventory and each source SDF/audit identity and hash;
- ligand-preparation provenance and optional ligand-generation provenance;
- Vina protocol identity and expected MODEL labels;
- required run status, output, pose-metrics, ensemble-analysis, summary,
  attempt-manifest, state, and completion records;
- every artifact hash recorded by the completion marker.

Directory existence alone never qualifies. An incomplete, corrupted, or
identity-mismatched candidate is preserved and reported as requiring a new
manual retry decision; it is not silently reused or overwritten. Valid
completed candidates remain reusable when a later candidate in an interrupted
batch has not yet started.

The unified Top40 conformer-generation lineage is not yet frozen. Its absence
is recorded as an external production-readiness dependency, not a software
failure. When generation provenance is present in a future formal inventory,
it participates in the attempt identity and resume comparison. Historical A4
or B3 lineage is never hardcoded as a production requirement.

## CLI and exclusions

The V0.5-A arguments remain available. `--dry-run` preserves the zero-process
planner. New production execution requires `--execute`; `--resume` is reserved
for a compatible existing batch. Exactly one mode is required, with no implicit
real-execution fallback. There are no force, aggregation, merge,
visualization, ranking, V0.5-C, or V0.5-D options.

The two modes are deliberately explicit:

```text
python scripts/run_batch_v05.py ... --candidates A4 --dry-run
python scripts/run_batch_v05.py ... --candidates A4 --execute
python scripts/run_batch_v05.py ... --candidates A4 --resume
```

Omitting the mode is an error, so a formal run must explicitly select
`--execute` after saving and inspecting the dry-run JSON. All three modes are
mutually exclusive. The output root must be below `--data-root`, which keeps every
generated V0.4 analysis spec relative and portable. Normal execution refuses an
existing output root; resume requires its immutable `batch_manifest.json`.

The completion contract hashes the runtime spec, protocol, copied receptor
bundle, every conformer's standardized SDF, prepared PDBQT, config, input gate,
Vina output/log/status, pose metrics and post-docking gate, the generated
ensemble spec, all ten V0.4 analysis outputs, and the full append-only state
history. `candidate_summary.tsv` must contain exactly one matching candidate row
with `analysis_status=PASS`; warning counts and scientifically weak results do
not constitute technical failure.

## Current external readiness dependency

The unified Top40 ligand/conformer generation protocol is not yet frozen in the
formal inventory. V0.5-B records
`UNIFIED_TOP40_LIGAND_GENERATION_LINEAGE_NOT_FROZEN` in candidate identity when
that provenance is absent. It neither invents lineage nor treats this project
readiness gap as an execution-software defect. Formal ligand approval remains
controlled solely by the canonical V0.5 inventory.
