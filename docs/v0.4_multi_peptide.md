# V0.4 multi-peptide generalization

V0.4 makes the V0.3 ensemble engine candidate-agnostic while retaining the
V0.1/V0.2/V0.3 regression fixtures. It does not compare candidates that were
docked under different protocols as if they were a formal ranking.

## Score semantics

The primary Vina score is parsed from each real `MODEL N` block's single
`REMARK VINA RESULT` record in the docking output PDBQT. The corresponding
pose-metrics score is a cross-check source, aligned by MODEL label at a fixed
0.001 kcal/mol tolerance. Missing, duplicate, mislabelled, or mismatched scores
fail the run before a final analysis package is published.

`vina_score_summary.tsv` reports raw and representative-eligible statistics
separately for the peptide and each conformer. Filtered poses never enter the
eligible statistics. `candidate_summary.tsv` is a one-row machine-readable
summary containing identity, protocol status, comparison protocol ID, score
statistics, recurrent core, representatives, and warning/error counts.

## Protocol identity

`screening_protocol_status` is either `formal_standardized` or
`legacy_regression_only`. A4 historical data are retained as legacy regression
only. B3 is the first formal standardized fixture.

The B3 `comparison_protocol_id` is the SHA-256-derived identity of ligand
preparation, group/template, receptor PDBQT hash, docking box, Vina
version/scoring function, exhaustiveness, requested mode count, energy range,
seed, and CPU protocol. Formal candidate ranking is valid only within an
identical comparison protocol ID; cross-template comparisons are exploratory.

## Receptor registry

`specs/receptor_registry_v04.json` is the single machine-readable source for
the A/B/C/D template bundles. Group is the only switching entry; monomer PDB,
receptor PDBQT, dimer PDB, target residues, locked hashes, and Vina box are
resolved and preflighted together. Unknown groups, missing files, hash
mismatches, cross-template combinations, and diagnostic `SERorder_test` files
fail without fallback. C/D must use their accepted normalized production
monomers. The normalization rationale and audited hashes are recorded in
`docs/receptor_normalization_cd.md`.

The receptor PDBQT identity and box used to derive `comparison_protocol_id`
come from the resolved registry bundle. The registry is also hash-locked by
each V0.4 spec and recorded in analysis summaries and manifests.

## Formal B3 preparation and serial docking

B3 uses the three preselected GPT/manual standardized SDF coordinates without
regeneration: sequence `IPVGNCRYMQ`, formal charge +1, protonated N terminus,
deprotonated C terminus, protonated Arg, standard L amino acids, and no
artificial disulfide. Meeko 0.8.0 freezes peptide N-CA and CA-C bonds.

The preparation audit verifies the source and copied SDF hashes, formal
chemistry, atom inventories, Meeko atom mapping, TORSDOF, receptor hashes,
receptor-registry hash and bundle preflight, generated config, and coordinate identity within PDBQT's
0.001 Å serialization precision. It refuses to overwrite any artifact.

The three Vina jobs are run serially. Each conformer must pass a pre-docking
gate, Vina exit normally, yield parseable MODEL/ENDMDL blocks with one score
remark per MODEL, generate pose metrics, and pass a post-docking score/hash
gate before the workflow proceeds. Requested `num_modes=20` is not treated as
the actual count; the B3 ensemble spec records counts parsed from outputs.

## Contact and legacy metric semantics

Formal direct and near contacts retain the frozen heavy-atom definitions:
direct is distance <=4.0 Å and near is 4.0 < distance <=5.0 Å, using the receptor
monomer PDB and explicit chain. No rounding occurs before classification.

The standardized pose-metrics generator labels legacy-compatible fields
explicitly. `legacy_5A_receptor_contact_fraction` is the fraction of peptide
residues contacting any chain-A receptor heavy atom at <=5.0 Å. Receptor and
chain-B clash pairs use heavy-atom distance <2.0 Å. The legacy composite
`basic_geometry_pass` remains provenance only and does not control V0.4
eligibility.

## Outputs

V0.4 retains all eight V0.3 files and adds:

- `vina_score_summary.tsv`;
- `candidate_summary.tsv`.

Every version-controlled spec uses paths relative to `--data-root`; actual and
optional expected SHA-256 values are recorded in the manifest. Analysis
packages are staged and atomically published only under ignored `test_output`.

`candidate_summary.tsv` contains exactly one row per peptide. Its frozen merge
contract includes identity, conformer and pose counts, raw and eligible Vina
statistics, recurrent-contact and representative counts, a stable analysis
status enum, and separate SHA-256 fields for the source spec, receptor registry,
receptor monomer, docking receptor PDBQT, receptor dimer, and frozen chemistry
contract. Best-score pose IDs remain independent of contact-pattern
representatives.
